# Niche SEO and GEO core

Turn verified market observations into useful pages and measurable business outcomes. Treg supplies observations, not a ranking strategy or a guarantee. Treat topical authority as demonstrated depth, useful original evidence and trustworthy recognition; never invent a Google topical-authority or E-E-A-T score.

## Choose the work and preserve the existing core

For this network use [the automation integration contract](references/studio-integration.md). The repository's `SKILLS/niche-seo-geo-core` is the maintained source; synchronize personal installations from it. It supplies research to the existing planner/builder/audit, whose schemas and publication contracts remain authoritative. Do not maintain a parallel calendar, release pipeline or SEO implementation.

Read the domain's current brief, business model, page inventory, research and applicable AGENTS.md. Distinguish live production, local preview, approved release and planned content. Reuse useful research and stable URLs. A full niche map is separate from the initial release subset; no default publishing quota, word count or fixed article total.

For this user's niche network, when present, read `TOPICAL_CONTENT_CORE.md`, `SEO_GEO_CORE.md`, `CONTENT_CORE.md` and `SKILLS/niche-content-planner/SKILL.md` in the current project. Follow their schema, domain, revision and release contracts. This skill adds research and decisions; do not create replacement canonical, schema, sitemap, link resolvers or publication filters. A user-level installed skill is not proof that the content studio injects it or that its instruction fingerprints changed.

For a topical plan or structural refresh use the planner's `references/planning-decisions.md` checkpoint when present: show query-to-URL decisions before dates, then verify their handover to the actual writer. Load it for planning rather than repeating niche research in every draft.

Select the needed mode: catalog audit, domain baseline, strategy/map, authorized implementation, or measured refresh. Audit requests authorize evidence gathering and a concrete backlog, not a production deployment or backlink campaign. Respect existing authorization and spend limits; do not ask again for authorized work.

## 1. Establish a baseline and a question worth buying data for

Record domain/siteId, market, language, date/timezone, paying customer, useful conversion, current fulfilment and permitted spend. Keep unknown sales, economics, expertise, stock and contact details unknown. Inspect publicly eligible URLs, robots, sitemap, metadata, article bodies and links with bounded read-only fetches. HTTP 200 and a sitemap entry do not prove Google indexing. Preserve failed requests and dates.

Discover Treg access: use available MCP catalog/search/get/call/balance tools, otherwise the authenticated CLI. Check `balance`, `tool ls` and `connections ls` without displaying credentials. Missing login is a specific Treg blocker; continue public/local analysis, but do not fabricate Treg calls or request provider keys. Read [Treg selection and execution](references/treg-playbook.md) before paid work.

Prefer first-party GSC/GA4/account data if actually connected and scoped to the domain. Without it, mark indexing, impressions, conversions and revenue unverified. External ranked-keyword and traffic estimates are not the owner's analytics.

Before new-site planning or a meaningful SEO refresh, gather the relevant observations, retain raw results and import a private site-scoped bundle through the common `seo-research.mjs` interface. Read [studio integration](references/studio-integration.md) for freshness, locale, snapshot and budget rules. Recheck evidence each new task; do not purchase all metrics for every article. A previous task's cap is not recurring spend authority. Read-only JSON generation uses supplied evidence and executes no paid calls; its invoking agent performs scoped research outside that step.

For each proposed data call, state the decision it can change: merge synonyms, choose page type, prioritize a cluster, inspect a technical failure, or validate a citation opportunity. Catalog discovery is inexpensive; endpoint execution may be metered. Batch flat-priced keyword requests and reuse saved results. Avoid buying the same capability from many providers unless disagreement matters.

## 2. Resolve market coverage before interpreting metrics

Read the endpoint's exact input, response, cost modifiers, serving mode, observed reliability/sample size and last success. Confirm supported country+language for that product: live SERP, Ads volume, Labs, AI mention database and AI UI sampling can have different coverage. Never silently replace LT/lt with US/en. A cheaper endpoint that ignores geography does not answer a Lithuanian-market question.

Sample representative head terms, long tails, important synonyms and different customer jobs with controlled locale/device/depth. Open relevant ranking pages to classify their actual function. Preserve query, requested/effective locale, device, returned URLs, organic/absolute ranks, data timestamp and sample depth. Record zero, null, empty, unsupported and failed as distinct observations.

Search-volume estimates can group variants and suppress sparse data. CPC and Ads competition describe advertising, not organic keyword difficulty. Do not sum close variants as independent demand. Trends are relative interest within a chosen geography, window and normalization, not absolute searches. Database competitors and keyword positions can lag live SERPs.

## 3. Convert questions to a bounded topical and intent map

Read [intent and original value](references/intent-quality.md). Map the owner-confirmed niche across understanding, options, selection, scope/cost/time, preparation, use, problems and next action where applicable. Reconcile the existing catalogue and every current useful URL. Build the full map even when only a small subset is ready to publish.

For each question choose: existing URL section/refresh, distinct new URL, merge, or justified exclusion. Use observed SERP overlap and customer job together; overlap is evidence, not a universal numerical rule. Split only when the answer or useful page function differs. A commercial catalogue SERP cannot be satisfied by pretending that an editorial guide has checkout or stock. A guide can address a distinct research job with verified options and an honest next action.

Per planned URL specify: reader question and decision, primary query/variants, intent and page type, cluster/root, existing path/id, original contribution, claims and required evidence, useful format, internal paths, CTA target/readiness, current data gaps and priority rationale. Match parent scope to children. Link when it advances a reader's decision; no all-to-all or owned-domain link quota. Stable historical paths and redirects require semantic review, not automatic archive resurrection.

Prioritize by customer value, fulfilment fit, relevant demand, observed intent gap, achievable original contribution, seasonal timing and implementation effort. Show the inputs and uncertainty; avoid made-up precision from a multiplied SEO score. A sparse query can be valuable when it solves a consequential customer need. Keep coverage planning separate from proof of page quality.

## 4. Implement and verify the authorized improvement

For technical work inspect actual production HTML and, when needed, browser-rendered DOM: status/redirects, one authoritative title/description/canonical, language, public index directives, crawlable links, accurate schema, dates, images, mobile rendering and useful error pages. Inspect facet/sort/search URLs separately from editorial pages. Local scores and lab performance do not prove field CWV or launch quality.

Write metadata as an accurate promise of the page's distinct answer; avoid rigid character quotas, keyword stuffing and clickbait. Keep H1 and snippets intelligible. Robots controls crawl, noindex controls indexing; a blocked crawler may not see noindex. Match schema to visible, real facts; Article/Organization/Breadcrumb can fit a guide, while Product/Offer/reviews require the actual corresponding offer and evidence.

Before content acceptance verify claim-level primary sources, concrete original value, authorship, media provenance, useful links, mobile reading and a functioning truthful CTA. Do not fabricate product testing, experts, reviews, stock, prices or delivery promises. For network work retain revision-bound review and atomic related-page release. Implement existing publishable dependencies before creating dangling links. A report, schema change or local test is not deployed work.

## 5. Measure GEO as sampling, not as a secret ranking layer

Read [GEO and measurement](references/geo-measurement.md) when AI visibility is in scope. Use realistic unbranded prompts, fixed market/language and recorded engine/surface; distinguish a live consumer search scrape from an LLM response API and a historical mention database. Separate brand awareness from URL citations and recommendations.

Keep prompts fixed across baseline and follow-up. Repeat a small number when budget permits, forcing fresh observations where supported. Record failed/unsupported results and cache/replay status. Inspect citations against the underlying documents; an AI answer is not factual source evidence. Report numerator and denominator per engine, language, prompt cohort and successful sampled responses; show the small-sample limitation. Branded prompts are diagnostic and must not inflate an unbranded visibility metric.

Improve reliable, extractable answers and original attributable material readers can use. Check search crawler access including actual CDN/WAF behaviour; allowing training bots is a separate decision. `llms.txt` can support reading but is not a Google AI requirement or citation guarantee. Never use hidden model-only claims, prompt injection or bulk forum/link spam.

## 6. Deliver decisions and close the measurement loop

Read [evidence and output contract](references/evidence-contract.md) for audits, plans and refresh work. Deliver the baseline, supported opportunities, ordered executable backlog, unresolved blockers, evidence links, authorized implementation checks and exact per-call spend. Label planned, implemented, tested, released, deployed, indexed and converted independently.

When data exists, compare relevant cohorts by query/page/cluster, country/device, brand/nonbrand and publication age. Use GSC for search exposure, analytics for visits/events and the inquiry/order system for qualified leads/revenue. Explain seasonal shifts, traffic mix, partial dates and attribution limits. Check deployment/indexing before declaring a niche has no demand. CTR can change when position or result features change; a before/after movement alone is not causation.

Set a suitable review point based on crawl/indexing readiness, available observations and seasonality; there is no universal ranking deadline. Do not create a recurring automation unless requested. Refresh, merge, improve discovery or strengthen a real offer based on the diagnosed cause. Continue all authorized executable work; finish with precise remaining external dependencies instead of a perfect-SEO claim.

## Optional bounded execution helper

`scripts/run_plan.py` dry-runs a reviewed JSON manifest by default and executes only with `--execute`. It calls the authenticated `treg` CLI, uses request files, keeps per-call responses/idempotency keys and records Treg settlement metadata. It is a transport/evidence helper, not automatic endpoint discovery, pricing approval, task-success validation or an authorization checker. Read its CLI help and [execution reference](references/treg-playbook.md) first. Run it only after reviewing current endpoint docs and the manifest's bounded inputs, purpose, cost and scope.
