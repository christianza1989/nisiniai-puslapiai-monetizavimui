# Acquisition projection v1 — candidate0.1.0

The dashboard and director chat must consume **one exact current snapshot** from the shared deterministic read tool, instead of counting native buffers, interpreting historical ACKs or asking a model to invent metrics. [projection.py](../../runtime/src/pinet_core/acquisition/projection.py) exports CaptureLedgerSnapshot; [schemas.json](schemas.json) is generated by `uv run --locked python scripts/acquisition_projection_contracts.py --check`.

This candidate is an **internal capture-only read library**. There is no mounted portal/director/report route, registered generic agent tool or new identity authority. The control owner must derive the full scope and adapter from the current authenticated business membership/grants, never a browser-supplied Scope; portal and chat then receive the same DTO. Reading a foreign internal scope returns no matching ledger rows; that is RLS evidence, not an HTTP authorization/404 acceptance. Production scope is rejected. No control/tasks/portal/migration source changes or daemon is implied by this library.

The tool opens one PostgreSQL **REPEATABLE READ, READ ONLY** transaction before queries and applies all five acquisition scope settings. Counts, current invitation/conversion, source watermark and bounded activity come from that single committed snapshot. A concurrently committed campaign stop cannot produce half-old/half-new counters. Each new query may observe the newer state; a returned snapshot remains frozen. `data_as_of` is the DB read transaction time, `expiry_evaluated_at` the aware clock used for expiry, and `last_committed_receipt_at` the source receipt watermark. They do not claim the remote native outbox is fully drained.

Metric definition **acquisition-capture-ledger-v1**, period basis **current_and_all_time_ledger**. This candidate is not a daily/weekly or occurrence-time report. The ledger stores receipt arrival time, not full native occurrence history. Later period reports must define that source/denominator and cannot relabel these counters as “this week”.

| Field | Exact meaning |
| --- | --- |
| campaigns / stopped_campaigns | Registered scoped campaign rows / paused rows |
| invitations | All scoped invitation rows, including retired |
| available_unbound_invitations | Unretired, no account binding, before original expiry, campaign not stopped |
| expired_unbound_invitations | Unretired/no account binding, original expiry passed, whether paused or not |
| retired_invitations | Native retirement/deletion facts recorded in core |
| currently_bound_recipients | Account binding exists and invitation is unretired; marketing expiry does not erase it |
| currently_attributed_providers | Provider binding exists and invitation is unretired |
| active_providers_in_core | Current unretired core conversion profile_active=true; not an independent live native eligibility check |
| historical_recipient_bindings | Distinct invitation refs with committed successful proof receipts, including later retired |
| historical_active_providers_in_core | Distinct provider refs whose committed event receipt once had profile_active=true; preserved historical result, not current activation |
| committed_commands | Unique scoped durable successful command receipts; exact retries do not add rows |

Unconnected discovery, outreach sent, received replies, remote pending outbox, failed attempts and cost are **null**, not zero. Failed HTTP/proof attempts are not stored in this successful receipt ledger. These figures require their actual source. `missing_sources` names explicit pending dependencies; full_pipeline_accepted and external_sent are strict booleanfalse. Fixture facts remain test-scoped and cannot become production business outcomes.

Recent activity exposes only operation, UUID, committed_at, outcome and optional native revision, newest50 with explicit `activity_truncated`. It is a committed-command list, not a complete attempts/inbox log. Raw receipt/request bytes, emails, account/provider/profile/ref/nonce/key material and hashes never enter this DTO. Historical `recipient_bound` activity can coexist with current bound0 after erasure; consumers must use current counts for current state. The snapshot's content_sha256 fingerprints canonical sorted UTF-8 JSON excluding that hash field; it is not authentication or proof of an unrelated source release.

Actual acceptance uses the existing isolated PostgreSQL lane: active→retired with old proof ACK replay still current0/historical1; redaction and nullable missing metrics; schema primitive rejection; foreign scope, pause/expiry; bounded real51commands; scoped campaign joins; and a real committed stop on a separate connection between report reads. Core/portal/director HTTP and generic tool adoption remain pending owner work in issue66. No separate UI counter implementation should be accepted.
