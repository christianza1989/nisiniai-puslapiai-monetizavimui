# Verslomatika native GUIDE work

This slice runs one actual planned page after an accepted customer creation revision. It uses the maintained `content-studio/scripts/customer-content-write.mjs` bridge and native V2 blocks, without converting rich content to business Draft sections.

The new `content-work.v1` contract is `docs/contracts/verslomatika-customer-content-work.openapi.json`, regenerated by `runtime/scripts/customer_content_work_contract.py`. Legacy creation.v1, team.v1 and content.v1 bytes stay unchanged. content.v1 remains an immutable intake snapshot. GUIDE job status is current; page readiness in a completed job is explicitly a `private_write_snapshot` observed at its actual write time.

## Customer path

All routes use the existing shared bearer Session, customer transport guard and current verified owner scope:

- POST `/customer/v2/creations/{creation_id}/content-work`: `{accepted_revision, page_id, idempotency_key}`; returns202 JobView.
- GET the same path: bounded20 jobs.
- GET `/{job_id}`: job, at most6 real role attempts, bounded immutable timeline, exact native candidates/review decisions and their SHA.
- POST `/{job_id}/cancel`: current cancellation; previous text and evidence stay preserved.

The caller selects an actual pageId with a planningBrief from the accepted intake. Arbitrary workspace paths, host changes, model choice and tool policy are never customer input. A page without its actual planning brief, wrong current accepted revision, changed manifest/source bytes or intake identity stops before a provider call. Idempotency replay returns the original job; changed input conflicts. The server owns all runtime artifact locations.

## Execution and safety boundaries

`customer_content_work_worker.py check|once|worker` is an explicit local entrypoint. Its source preflight requires a clean exact pinned Git checkout, loopback/local feature configuration, a restricted PostgreSQL role and the actual RLS schema. This implementation did not run the real worker or call a provider. The parent owns source adoption, API/worker startup and actual customer UI trial.

The GUIDE has its own job, immutable role attempts and immutable events. It does not attach new work to a succeeded private creation job. The fixed creator, critic and coordinator use the existing no-tools read-only CLI transport, fixed gpt-6-luna, ignored user rules/config, bounded private output/trace files and current authorization supervision. No shell/MCP/browser/web/email/paid research/media/publication capability is enabled.

At most2 rounds,6 attempted dispatches and300 seconds total, including studio preparation/validation/application. Every attempted dispatch reserves before provider execution. Finite per-customer and global daily provider limits include original creation-team attempts, legacy private calls and native GUIDE attempts; failed, cancelled or revoked reservations never refund. Separate GUIDE job admission counts bound queued/failed admissions too. One GUIDE can be active per creation, and there are at most20 GUIDE jobs per creation.

A first-round structural/link/media output failure is kept as a real failed, charged creator attempt. Only the remaining second creator round can repair those specific maintained validator codes. No critic verdict is invented and context/CAS/source/auth failures are never repaired by weakening a gate. A second failure ends the job. The semantic critic may request the ordinary second full creator/critic/coordinator round.

Both workers share exactly the PostgreSQL `creation-execution:<environment>` advisory execution barrier. The GUIDE cannot release it through API cancellation; the owned process is stopped before execution returns. User/Session/Creation/Job locks, exact source revision, run identity, current accepted revision, unexpired lease and absolute deadline fence claim, reservation, heartbeat and write. A stale running lease is failed without automatic retry.

The native nonmutating `validate` command checks the exact manifest/context/content/planning hash, normalizes with the maintained native V2 implementation and checks actual same-site IDs, existing verified external URLs and assigned media. It returns the exact canonical candidate/hash for critic review and leaves site, source and manifest bytes unchanged. Existing prepare/apply behavior and atomic model content/planning/site CAS are preserved.

The critic receives that complete native candidate and its original canonical SHA, all server observation receipts and exact allowed JSON pointers. Known language failures are projected with index-preserving placeholders only in model input; original private candidate/trace is retained. Native review reuses the existing strict receipt aggregation and role schemas at stage content, without business-Draft normalization. The coordinator cannot omit required corrections, disagree with the critic's disposition or hide FAIL/UNVERIFIED observations. The writer only applies an accepted candidate with observed automatic language PASS. This screening and model criticism do not establish perfect human editorial quality or any source/media/browser verification.

Private application holds authorization locks across the maintained Node CAS write. Cancellation/revocation/revision therefore linearizes before or after that write. PostgreSQL and the local studio file are separate durability systems: a process/DB failure after an atomic private file write can leave an uncertain completion. No automatic replay or public approval is inferred; preserve exact private output/file evidence and reconcile before a new job. A deadline crossing after write is reported as `apply_completion_uncertain`. Startup after an interrupted lease reports `worker_interrupted`.
