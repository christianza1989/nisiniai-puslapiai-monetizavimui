# Opt-in checkout continuation and one operational reminder

`paymentRecovery` is an explicit per-store policy, disabled when absent. It supplies `enabled`, `reservationHours` (1–24), `reminderAfterHours` (1–23, less than reservation), `enabledAt`, `noticeVersion` and an HTTPS `origin` in the store's admitted hosts. Other stores retain the original one-hour reservation. The current reminder copy is Lithuanian and eligibility is restricted to LT orders.

The checkout renders the notice at email capture and submits its exact version. The immutable snapshot records the shown version; no old order is enrolled retroactively. Update the site's privacy information through its maintained content review/release workflow before activation. This is one neutral operational reminder within24h, not marketing/newsletter consent. Owner authorization to enable a store does not authorize paid services or test messages to customers.

`COMMERCE_RECOVERY_KEYS` is a private JSON map of store IDs to independent random64-hex keys. HMAC capabilities bind purpose, environment, store, order and a30-day expiry. Email uses `/cart#resume=...`; the browser removes the fragment before use and posts it to the bounded same-origin `/api/payment-recovery` route. Analytics must use sanitized canonical page URLs. Never put the capability in a query, access log, link-tracking provider or report. Existing order access hashes are unchanged. A recovery capability permits only order/receipt reads and checkout; it cannot withdraw, download private documents, capture analytics, refund or operate the store.

The existing durable cron prepares at most one `PaymentReminder` per order. It reads the exact bound Stripe Session, checks unpaid/open status and PaymentIntent processing, current reservation, notice, age, withdrawal and replacement basket. No reminder without a persisted Session ID: a lost provider-create acknowledgement is not proof that no payment exists. Recheck before the conditional durable send claim. A payment can race an external mail delivery after the last provider read; no atomic transaction spans Stripe and mail. Never claim an absolute no-race guarantee.

`customer_notifications`/`notification_commands` and the private mail gateway keep their immutable first snapshots and one-shot claims. Unknown outcomes are reconciled by positive evidence, never blind resend. Paid, withdrawn, expired or replaced unattempted reminders are suppressed into review. No catch-up mailing to old orders.

Expired continuation requires positive expired/unpaid provider evidence before restoring the basket for a fresh quote, stock, shipping and terms review. It cannot revive a Session, reuse an expired delivery quote or automatically create a replacement order. An unrecorded Session or unknown/processing provider state blocks replacement payment until reconciled. Signed payment webhooks remain the only paid-state authority.

## Primary sender migration

The authenticated mailbox, store `notificationPolicy.from` and private gateway From must agree. `COMMERCE_MAIL_CONNECTIONS` optionally provides a map of already configured store IDs to exact `{sender,transportRef}` tuples; when present it is the maintained mail identity source for that store. It contains no Stripe/carrier credentials. Legacy combined `COMMERCE_CONNECTIONS[store].mail` remains the fallback for stores not migrated. Do not rewrite unrelated provider keys merely to change a mailbox.

Pause only notification sending briefly during a sender swap; checkout/payment and event persistence remain active. Capture exact config/bindings and outstanding commands first. Accepted commands remain unchanged. Previously attempted unknown commands can query their old receipt even after From changes; they can never be sent through the new identity. An unattempted immutable command with a different From remains a conflict for operator review. Re-enable after authenticating the exact mailbox and verifying a clearly labeled owner self-test through the actual Worker and an exact inbox receipt.

Hostinger HTTPS Mail API supports optional `html` with a text alternative ([official V1SendRequest](https://github.com/hostinger/mail-api-typescript-sdk/blob/main/docs/V1SendRequest.md)). Keep HTML bounded and part of the immutable mail fingerprint. No automatic SMTP or paid-provider fallback. Account/key creation and permissions still require actual owner authorization.
