# Acquisition adapter contract 0.1.1

2026-10-10. Candidate interface for the shared core, Madbeauty backend and Verslomatika. [Coordination issue66](https://github.com/christianza1989/nisiniai-puslapiai-monetizavimui/issues/66), dependency [PR59](https://github.com/christianza1989/nisiniai-puslapiai-monetizavimui/pull/59), [dashboard handoff](../../verslomatika-plan/INTEGRATION_HANDOFF.md).

**Implemented here:** strict Python contracts, generated JSON schemas, a pure conversion reducer, Python scoped HMAC verification, server Web Crypto signing/verification, and executable synthetic cross-language checks. **Not implemented by this package:** mounted HTTP routes, PostgreSQL replay ledger/outbox, scheduler, transport, production keys, Madbeauty binding or hosted acceptance. Do not advertise these endpoints as available until actual deployment capabilities confirm them.

Patch0.1.1 enforces primitive types from the JSON schema: boolean false cannot arrive as numeric0, booleans cannot arrive as strings, source_revision cannot arrive as string/bool and times use JSON date-time strings. Use model_validate_json on raw JSON. Wire records are immutable after validation. Original candidate0.1.0 remains in commit2082c6ba6f6c4bf45d783bd97167602de6dff0c8; no mounted client has been claimed, and the accepting site adapter must explicitly update its version.

## Canonical source and generated clients

[schemas.json](schemas.json) is generated by [acquisition_contracts.py](../../runtime/scripts/acquisition_contracts.py). Adapt native TS/JS/Python clients from it; do not maintain a second hand-written schema. Unknown fields/version fail explicitly. Breaking changes require a new contract major and coordinated adapter acceptance.

From `agent-business-core/runtime`:

```powershell
uv run --locked python scripts/acquisition_contracts.py --check
uv run --locked python -m unittest discover -s offline_tests -p test_acquisition_interfaces.py -v
node --test ../contracts/acquisition-v1/auth.test.mjs
```

Regeneration omits `--check`. The signature vector has a deliberately **public synthetic test key**, never a configured runtime secret.

## Proposed server routes

| Method / relative route | Input / output | Grant |
| --- | --- | --- |
| POST /integrations/acquisition/v1/sites/{site_id}/resolve-invitation | ResolveRequest → Resolution | resolve |
| POST /integrations/acquisition/v1/sites/{site_id}/events | LifecycleEvent → EventReceipt | events |
| POST /integrations/acquisition/v1/sites/{site_id}/capture-handshake | CaptureHandshake → identical validated shape | capture, test only |

Route site, request scope, grant scope, adapter and environment class must all agree. Host names are independently registered server configuration. Neither browser site_id nor shared operator Bearer alone establishes an end user's business membership. Verslomatika consumes its authenticated server adapter; no callback or operator keys in frontend bundles.

Use exact POST paths without query strings/trailing-slash redirects. Content type application/json; limit raw bytes to65536 before parsing; reject duplicate signature headers. HTTPS required off loopback. Test keys never have production grants. Resolve/events/capture are distinct permissions. Rotation uses distinct key IDs and an explicit bounded overlap.

## Raw-byte signature

Send X-Acq-Key-Id, X-Acq-Timestamp (Unix seconds), X-Acq-Signature (v1= lowercase hex SHA-256 HMAC). Secret is at least32bytes and supplied explicitly by private server configuration. Signature input has LF separators, no final LF:

```text
acquisition-v1
POST
<exact request path>
<timestamp>
<key ID>
<lowercase SHA-256 of the exact raw body bytes>
```

Sign serialized UTF-8 once and send those same bytes; the verifier must not parse then stringify before hashing. Python [transport_auth.py](../../runtime/src/pinet_core/acquisition/transport_auth.py) also verifies scope, adapter and permission. [server-auth.mjs](server-auth.mjs) uses Web Crypto in Node/Workers and verifies cryptography/time; the caller must separately verify the trusted grant's scope/adapter/permissions. Five-minute clock window is **not durable replay prevention**.

## Invitation and attribution

Core creates an unpredictable reference with at least192bits of randomness, stores campaign/prospect/contact binding privately and sends only the ref to the approved site signup route. An invitation grants no login, publication, auto-registration or contact permission. Never encode contact email/person/source URL in its public ref. Log only scoped internal IDs; ref itself is a bearer attribution token and must be scrubbed from analytics.

Madbeauty chooses its actual signup parameter/route after checking its current backend. Its owner later confirmed the current provider start /meistrui/pradzia through email-only /paskyra; /taisykles carries terms. Invitation support on these paths is not yet verified. Core resolve returns only purpose, offer revision, expiry and state. Native account verification must validate the intended-recipient binding server-side after actual OTP before attribution; a forwarded link alone cannot establish who joined. The concrete verified-address HMAC/challenge and email canonicalization are adapter dependencies, not a client-provided assertion. Never use a plain email SHA-256 as private recipient proof.

Unknown ref →404, expired ref before first attribution →410, stopped marketing sequence → available signup remains ordinary but acquisition ref is not reactivated. Already-attributed ref cannot silently bind another native provider. Conversion callbacks for a provider already validly attributed before expiry remain acceptable later; account removal/suppression processing must continue when the campaign is paused or expired.

## Native lifecycle and replay

Only the native authenticated Madbeauty backend emits LifecycleEvent; an LLM cannot sign a guessed success. Source revision is monotonic for the native provider aggregate **across all event kinds**, not a timestamp or counter restarted per kind. Source release identifies the deployed adapter. Native provider/profile refs are opaque tenant-local IDs, never email/display names.

signup_started → account_verified → profile_submitted each has profile_active=false. profile_active requires a native profile ref, operator_approved=true and actual eligibility_revision. Madbeauty applies its existing revision/offer/operator eligibility checks before emitting that event. profile_deactivated clears current active state; account_deleted is terminal. Historical activation and currently active are distinct metrics.

Core must bind ref→provider, atomically insert the durable receipt and update the scoped projection. Key: (business_id, environment_id, adapter_id, event_id); store a SHA-256 of the validated event bytes. Same ID/same bytes →200 duplicate with original receipt; same ID/changed bytes →409. Retry identical event bytes with a fresh signature timestamp. Older source revision is recorded stale and never rolls back the projection. Same aggregate/revision with different content →409, even if event_id differs. Serialize/CAS the aggregate; stale leased workers cannot overwrite a newer result. The pure reducer itself does not provide these storage guarantees.

The site needs a persistent outbox written atomically with its native state mutation. Retry bounded exponential backoff and expose permanently failed records to its operator. Replays do not create a second signup/email. Delete personal detail according to native policy while keeping the permitted minimal dedup/suppression receipt. Core must not turn model text, a captured email, a clicked URL or a synthetic response into native activation.

## Stop, capture and acceptance

Campaign pause stops new research/drafting/outreach but accepts native lifecycle, unsubscribe/complaint and requested privacy handling. Suppression is checked again at queue/claim/delivery; a campaign restart cannot clear it. The existing booking/login SMTP purpose guard stays unchanged.

First shared run: isolated test business/environment, example.test recipient capture, external_sent=false. Handshake only verifies that scope/version/mode can be exchanged; it does not prove SMTP delivery, paid discovery, registration, replay durability or a daily scheduler. Actual model calibration remains the separate [dialogue lab](../../acquisition-plan/CALIBRATION.md).

Before integration acceptance: actual site→core with persistent outbox/replays, changed-body409, unknown/expired ref, cross-tenant/test-production rejection, operator-approved activation, late/deactivated state, restart and stop tests. Then Verslomatika must show the same current metrics and evidence through actual deployed APIs. Publish exact source/schema/deployed versions in issue66, with local/hosted/model/mail evidence distinguished.
