# Normal acquisition capture adapter v1

Receiving workstream: [issue66](https://github.com/christianza1989/nisiniai-puslapiai-monetizavimui/issues/66).
This connects the existing PR59 capture ledger to normal core entrypoints; it is a foundation for the requested full Madbeauty integration. It does not finish discovery, generic daily tasks, correspondence, privacy Case handoff, director model tool, native normal adoption or ordinary portal UI.

## One authenticated read

`GET /operator/v2/businesses/{business_id}/acquisition`, mounted by both `pinet_core.api` and `pinet_core.control_api`. Business ID is a UUID. No query parameters, body Scope, environment, site or adapter selection are accepted. The existing local/hosted control transport guard and opaque bearer Session authenticate the principal. This capture slice additionally requires local mode/loopback PostgreSQL and a test environment; hosted capture is unavailable.

The endpoint returns the existing `portfolio.v1` envelope: `contract_version`, `environment`, configured `source_revision`, `observed_at`, `request_id`, `data`. `data` is exactly [CaptureLedgerSnapshot0.1.0](../acquisition-projection-v1/README.md), using the unchanged [schema](../acquisition-projection-v1/schemas.json). Envelope observation time is response time; the authoritative snapshot/expiry clocks are `data.data_as_of` and `data.expiry_evaluated_at`. A new read has a new observation/hash; compare current counts and the committed watermark, not hashes from separate reads.

`normal.read_snapshot(app,database,business_id=...,user_id=...,session_id=...)` is the shared internal boundary. Actor/session arguments must come from server authentication/task ownership, never model output or browser JSON. It checks the same current Session, enabled User, owner Membership/BusinessGrant, server business/site mapping and per-business module registration inside the same `REPEATABLE READ, READ ONLY` transaction as the ledger queries. The future director tool must call this boundary, rather than counting native queues or duplicating SQL. The internal boundary is tested; a director model tool has not yet been mounted.

Per-module `acquisition.read` permission, enabled registration, original approval lifetime and configured source revision are required. Foreign business is `404 not_found`; revoked/expired Session `401 unauthenticated`; invalid UUID/query `400 invalid_request`; missing read permission/stopped registration `403 acquisition_read_denied`; expired approval `409 acquisition_approval_expired`; changed source `409 acquisition_source_changed`; missing mapping `503 acquisition_not_connected`; disabled/changed/unreadable registration `503 acquisition_unavailable`. The existing transport/auth guard may return `403 control_unavailable`; DB failures use `503 source_unavailable`. Error bodies contain `code`, `message`, `request_id` and never private configuration. Responses are private/no-store.

Current and all-time counts, expiry semantics, recent50 activity, explicit truncation and redaction remain those of capture0.1.0. Disconnected discovery/outbound/inbox/cost figures remain null. `external_sent=false` and `full_pipeline_accepted=false` are strict booleans. Neither UI nor model may describe this as a weekly report, real delivered mail or completed platform.

## Server registration and normal migration

Default `acquisition_capture_enabled=false`. Explicit private absolute `acquisition_capture_config` must be inside this runtime's ignored `artifacts/` directory, with no symlink parents and a one-MiB limit. JSON `normal_capture_version=acquisition-normal-capture.v1` contains unique test Scope/adapter registrations, separate transport/recipient SecretStr hex keys and explicit existing callback permissions. SMTP and voice must stay disabled. Parser failures are fixed safe errors without raw Pydantic input/exception chains. No private registration is included in Git or a source-only transfer kit.

The normal schema is `0025_acquisition_core` after the reviewed `0024_xbot_module_flow`, not the historical proposed0012. It installs the four unchanged ledger tables and the additional `acquisition_modules` registration. Module approval is a trusted administrative action, with exact business/environment/site/adapter, approving owner/organization, explicit read/capture permissions, source SHA and fixed approval/expiry dates. Startup requires matching native registration and forced-RLS restricted-role storage. Disabled/expired modules may start so authenticated withdrawal can still be consumed; they cannot authorize new marketing/activation commands.

Runtime can only SELECT module registrations. Its scoped definer helpers return booleans and lock only the exact registered module and approving User/owner Membership/BusinessGrant. PUBLIC execution is revoked. They grant no general UPDATE authority and return no foreign identity/data. New commands pin these rows and use fresh DB time after the final module, identity, proof nonce or first-provider wait. A committed revocation serializes with an already admitted transaction; the next new command is denied. Exact old body/ID replay returns its immutable original ACK before current command admission and creates no new action. Same ID/different raw body conflicts.

`bootstrap.py` refuses a partial acquisition schema in one transaction and restores least privileges on the complete schema, including removal of any earlier broad receipt grants. Receipts remain SELECT/INSERT only; module mapping remains SELECT only; all acquisition tables force RLS. Existing control privileges are unchanged. An empty rehearsal can downgrade0025; any populated acquisition table refuses downgrade and preserves history. Source revert/held workers is distinct from erasing operational data.

Existing server-to-server callback paths and raw-body MAC contracts are unchanged. Native callbacks are not browser endpoints and their keys never cross the portal BFF. Withdrawal/deactivation/deletion can be accepted after campaign/module stop, expiry or approver revocation using the exact registered binding/proof; this does not authorize reactivation or resume. Historical activation ACKs remain historical after current profile withdrawal.
