# Build and delivery review

## Translate research into a brief

Write enough to implement without re-opening every competitor page: target reader, actual primary action, a small URL map, ordered sections and their role, style tokens and source evidence. Provide a desktop and mobile composition choice. Do not freeze a fixed section count, colour or font for all niches.

Use [design diversity](design-diversity.md) for network comparison, precise reference-to-section decisions, brand/asset planning and bounded customer tools. Document why this site's combined appearance differs from its nearest network neighbour; carry that plan through homepage, index, guides and form.

For every section specify: reader question; actual answer/data; layout; appropriate next step; proof or dependency. A catalogue grid requires real product data; a selection guide needs useful criteria; an information hub needs links to actual answers. Contact and privacy details must describe the actual operator and data flow before public launch. Unknown business identity/capacity stays a launch dependency, not a fabricated footer.

## Quality criteria

| Area | Passing evidence |
|---|---|
| Hierarchy | Site purpose and next action understood from the actual first screen; readable headings and balanced content density |
| Brand fit | Palette, typography, imagery and layout suit this niche; coherent design distinct from other sites without unnecessary custom infrastructure |
| Content | Each URL answers a specific question; title promise fulfilled; factual sources and useful original contribution; no repetitive filler |
| Responsive layout | Desktop and narrow/mobile screenshots inspected; no horizontal clipping, cropped controls, tiny text or hero image hiding meaningful content |
| Accessibility | Meaningful headings/landmarks, descriptive real links, labels, visible keyboard focus, adequate contrast and native form error behavior |
| Interaction | Primary action, guide navigation and actual form work; success means durable storage; email delivery assessed independently |
| Performance | Production mobile Lighthouse measured with actual assets; responsible image sizes; minimal client code and no gratuitous animation |
| Shared SEO | Existing host-aware core and publication filter reused; no canonical/schema/sitemap/LLM leakage or site-specific duplicated SEO code |
| Honesty | No fictional prices, reviews, people, completed projects, stock, partner network, delivery guarantee or renderer-only unapproved factual content |
| Phase fit | Supports interest testing and useful information; inventory, supplier automation and complete commerce deferred unless already authorized/available |

## Finishing procedure

For major redesigns compare genuinely different composition mechanisms, not merely different palette/font versions of the same split hero. Record similarities honestly. A seed/comp is a decision artifact, not proof of quality. Before each screenshot confirm the intended domain/title, successful HTTP response, loaded fonts and decoded nonbroken images; error pages and blank hero placeholders are invalid review evidence. Repeat these validity checks after a production rebuild. Pass focused-state captures when focus is a material finding.

Measure the actual rendered line when prose feels too wide; CSS `ch` can differ greatly from character count in the chosen typeface. Keep the same truthful native form and approved package source while changing presentation. Avoid loading every niche's CSS/fonts into one domain. Before a shared performance change, coordinate the common file, preserve other renderers, and verify real host-aware responses afterwards.

Inspect a real representative path: homepage → selection/guide → inquiry → confirmation, plus policy/footer paths. Check an invalid submission and storage failure behavior. Synthetic QA contact records stay local and are never imported as content. Test that other domains cannot access this site's unpublished routes/media. Check a future page remains private even when linked from an approved source.

For a complete phase-one domain task, use the project's `CORE_BUILD_CONTRACT.md`: the initial result includes the useful guide set with images, hub, contact/privacy path, project explanation, truthful editorial profile and information-use terms. Reuse existing shared SEO/media/backend functions; domain-specific composition remains a design decision. Start the audit with the shared initializer, never by copying another site's PASS snapshot. Verify actual enlargement separately using the audit skill's `references/accessibility-verification.md`; screenshots at a narrow viewport or a Lighthouse accessibility score alone do not establish text enlargement.

Record desktop/mobile screenshots, production mobile Lighthouse result and relevant tests with exact environment. Fix material regressions before handing back. Do not write a large test suite for cosmetic changes, but verify the real page visually; meaningful domain/publication/form changes require tests. Avoid repeated benchmarking once justified checks pass.

Return a concrete result with a usable local/live preview and precise state. Report remaining contact/operator/DNS/hosting/delivery/measurement dependencies only when actually unresolved. An asset preview or code diff alone does not finish a request for a website.
