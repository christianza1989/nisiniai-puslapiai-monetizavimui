# One business, several page languages

The studio accepts an optional BCP47 `locale` in createSite/editSite; existing sites retain lt-LT by default. A locale change invalidates review context through the existing review binding. It does not rewrite historical releases or establish a translation workflow by itself.

Hotube demonstrates an opt-in V1 presentation adapter under one `siteId=wildtubs-europe`, with `hotube.eu` selected by the owner. Localized routes and supported locales are declared once in the public companion's `config/site-languages.json`. `niche-languages.mjs` resolves language, page role and equivalent routes from that declaration and the caller's eligible public inventory. Root remains the default-language homepage; translated home routes use the existing service page bucket. No schema or alternate publisher is introduced.

Shared metadata/schema, breadcrumbs, sitemap and reading exports consume the same approved, revision/date/host-filtered pages. Alternate links are emitted only when the corresponding page is actually eligible. A new language requires actual edited copy, option terminology, registered routes, media/context review and the normal atomic release. Adding a locale code does not manufacture translated content or approval.

Product options are separate source data bound to an approved product page through its catalogue content hash in the existing intent snapshot. A public renderer or server request must resolve the eligible page first. Product identifiers and option identifiers are language-independent; prices remain EUR manufacturer references until actual distributor offer rules are established. Product schema does not invent a seller Offer from a third-party reference price.

The shared enquiry path can atomically persist a server-recomputed configuration with its lead in `niche_lead_configurations`, scoped by the same siteId. Caller totals are ignored; stale catalogues, unknown options, incompatible choices and foreign sites are rejected. This is a nonbinding enquiry, with no payment/order/stock or account entitlement.

Hotube release/adoption and future agent attachment are separate. Supported registry/BusinessGrant ownership must be established through the actual platform paths. Do not invent a Business UUID, CreationRegistration or native admission. A proposed future bridge is not a second agent/calibration core.

The completion inspector loads the companion locale adapter only when available, keeps legacy Lithuanian fallbacks, and uses a native bounded loopback HTTP request to preserve the canonical Host. Its rendered PASS is still separate from the A–Z score, browser review and launch acceptance. Original failures must remain available; a transport repair never rewrites an earlier report.

V1 product pages can contain up to 1024 responsive media variants through the shared studio/import path. V2 retains its separate existing 60-variant schema limit. Dynamic option data, device save/share and optional-photo presentation remain a business adapter; source facts and media rights require their own evidence. No provider execution or channel activation is authorized by this protocol.

The paired common-code PR intentionally contains no manufacturer media, business content package or active catalogue registration. The actual Hotube candidate stays local because both configured GitHub repositories are public and manufacturer reuse rights have not been confirmed. The optional route declaration alone grants no content or publication; existing sites retain their original behavior. After rights/authorization, the separately reviewed site candidate can be transferred without creating another core.
