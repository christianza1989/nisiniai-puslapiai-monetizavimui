# Phase-one niche website acceptance

For research-dependent SEO/GEO findings apply [niche-seo-geo-core](../niche-seo-geo-core/SKILL.md) and its [automation/evidence contract](../niche-seo-geo-core/references/studio-integration.md). Check actual locale, dates, raw evidence and missing/stale observations; do not inherit another site's metrics or an old PASS. This skill retains the full A–Z acceptance; a Treg dataset or loaded instruction fingerprint does not certify the site.

Read [the shared project skill contract](../PROJECT_CONTRACT.md) for reconciled helper roles, real contact/source authority and publication/media boundaries. Imported SEO or UX checklists contribute focused evidence; they do not replace this A–Z acceptance or establish readiness independently.

Use this skill when a niche site needs a complete acceptance audit, benchmark review or launch-readiness assessment. It does not create commerce, supplier, voice or account systems merely because a domain resembles a store. The owner's explicit request decides whether this is report-only or includes repairs.

Read project `AGENTS.md`, `START_HERE.md`, `WORKSTREAMS.md`, `SEO_GEO_CORE.md`, `MAIL_CORE.md`, `NETWORK_LINKING.md`, the site's brief/history/DESIGN, current content-studio record, approved package and real renderer. Reserve actual write boundaries. Preserve other sessions' files, domains and processes. A previous passing audit is reusable evidence only when its target, version, environment and relevant facts remain current.

## Audit contract before repairs

For a new niche inspect the depth of the business-selection evidence: buying intent, local/international offers, viable monetization alternatives, fulfilment constraints, honest economics and a falsifiable initial test. Missing market data stays unknown; no mandatory invented traffic/margin estimates. A document heading or source list alone does not establish a researched decision.

First inspect the site's `BUSINESS.md` and the builder's [business validation](../niche-site-builder/references/business-validation.md). Check the actual customer, paid outcome, plausible revenue path and honest phase-one intent signal against the rendered offer. Technical completion cannot rescue an owner-rejected business direction. Do not substitute topic submissions, article views or newsletter signups for demand for a named paid product/service. Apply this to A/D/F/G/V with evidence; preserve explicitly chosen publishing businesses with a concrete payer/test, and don't imply that a business hypothesis is validated demand.

Read [the A–Z checklist](references/checklist.md) and [report/scoring contract](references/report-contract.md). Create `sites/<siteId>/PHASE-1-AUDIT.md` and a JSON record. Map every criterion to `PASS`, `FAIL`, `UNVERIFIED` or justified `NA`. Empty checkboxes and missing evidence remain unverified. Record baseline findings before changing code; label priorities, impact, owner, proposed repair and acceptance evidence.

For a new site, initialize the complete catalog from the project root with `node SKILLS/niche-site-audit/scripts/init-audit.mjs <siteId> <canonicalHost>`. It starts all 85 criteria UNVERIFIED and preserves an existing audit. Do not copy the tractor site's statuses/evidence or its site-specific writer as a passing template. For R2/S2 read [enlargement/reflow verification](references/accessibility-verification.md); unsupported shortcuts or interrupted Computer Use do not prove enlargement.

Inventory every public URL and representative private/future/unknown URLs. Audit homepage, index, **all initial guides**, contact/privacy/trust/profile pages and a real 404. Article quality is not proven by word count or three titles. Require a distinct answered question, correct evidence, useful examples/checklist, visible attribution/date, navigation and an honest next step. Authors can be real organizations; never fabricate a person, qualifications, hands-on test, customer or partner to fill E-E-A-T boxes.

## Evidence and applicable requirements

- For every new site's local acceptance inspect `sites/<siteId>/CONTENT_READINESS.md` against project [content-ready build gates](../../CORE_BUILD_CONTRACT.md#turinio-priėmimas-privalomas-kiekvienai-naujai-svetainei) and [CONTENT_CORE.md](../../CONTENT_CORE.md). Require current siteId/policy, package import, private draft, real article/index rendering and isolated actual HTTP evidence before/after publication for the page, prepared links and SEO/LLM projection. Map the evidence to existing applicable A–Z criteria; do not upgrade historical audits or treat a planned calendar/shared unit test as this site's passing integration. Future content counts and deployment status must remain literal.

- Inspect source and **rendered production HTML**. Crawl host-aware canonicals, headings, metadata, breadcrumbs, JSON-LD, internal/fragment links, assets, sitemap, robots and LLM exports using the actual public projection. Check approved/hash/date/host/deployment boundaries together; do not build a second publishing predicate in the auditor.
- Review real desktop/mobile screenshots before automated aesthetic findings. Use the existing builder/Impeccable adaptation for design, planner for factual/editorial repairs and web-perf for measured performance. Recheck layout after longer posts, source lists and bylines. A clean detector and Lighthouse do not prove craft, WCAG conformance or conversion.
  For new identities inspect [design diversity](../niche-site-builder/references/design-diversity.md) and compare the nearest network designs, actual reference pages and planned asset roles. Report cosmetic substitution and repeated image language even when technical checks pass. Verify any included calculator/comparison's inputs, rules, limits and useful result; phase one does not forbid a bounded tool. Keep first-result scores tied to their captured catalog; later requirements do not rewrite earlier evidence.
- Inventory visual coverage URL by URL. All initial guides need an inspected subject-specific image. Homepage needs purposeful supporting assets beyond the opening; index previews use the correct guide image. Keep technical diagrams in accurate HTML/SVG when appropriate, without treating them as a substitute for requested raster imagery. Legal/privacy pages can stay text-focused with a recorded reason. Check actual image/srcset requests, sizes, mobile focal points, alt, Article image and loading; a prompt or media record without rendered pixels does not pass. The owner does not want ImageGen/model/tool badges on original imagery. Retain provenance privately and editorially, preserve any genuinely required third-party credit, and never imply a stocked product or real client project.
  Verify the shared import path against project `MEDIA_CORE.md`: actual source decoding, responsive family attachment, EXIF/alpha/no-upscale and source-original isolation, not only a WebP filename. New agents use the shared importer; older approved immutable bytes need no silent migration. Automatic optimization does not prove appropriate CSS sizes or topic-specific visual quality.
- Validate actual schema meaning against visible content, not merely JSON parsing. Breadcrumb paths and article identity/dates must agree. Optional image/person/product/FAQ/rating markup is not a quota. Avoid LocalBusiness/Product/Offer/review markup without the real corresponding capability and evidence.
- External sources need a useful claim, primary source, retrieval date and current target. Own-domain editorial links require real target IDs, publication and deployment eligibility. No all-to-all links, backlink quota or concealed ownership. Revisit planned links when their target becomes public. Inspect links actually rendered in prose as well as related/source panels.
- Legal/privacy review is based on current primary guidance and actual data inventory. Do not copy a universal e-shop policy into an inquiry-only pilot, invent legal identifiers, storage periods, processors, transfer assurances or a working deletion process. State unresolved launch facts in the private audit. Necessary operational storage, consent/notice, marketing permissions and measurement are different purposes.
- Exercise real form validation and durable storage in a clearly marked test environment. Operator transport acceptance and matching INBOX receipt are separate checks. Avoid contacting clients. Existing receipt evidence can be reused with its exact limits. Audit rate protection, recovery and data lifecycle; do not erase real leads as a test.
- DNS/HTTPS, actual domain deployment, GSC/indexing, production D1/mail/limits/privacy and genuine demand cannot be proved on localhost. Mark them separately as launch/operations evidence. Archive access errors are not an empty history; retain URL decisions without copying old claims or creating irrelevant redirects.

## Repair, confirm, improve the core

Implement verified in-scope defects in a coordinated batch. Facts/content go through the studio, claim review, exact revision approval, export/import and compile; never hand-edit an approval hash. Add schema fields only for a concrete need and update both validators plus integration tests. Prefer shared author/breadcrumb/date/link utilities to per-domain SEO copies; preserve each niche's composition.

After shared changes run `npm run test:core` and `npm run test:seo-smoke` for every current niche. Add meaningful regressions for publication/tenant/schema defects. Build in a reserved window or isolated copy; do not package credentials. Use real production pages and images for Lighthouse and browser confirmation. More iterations need a specific unresolved defect, not a desire to inflate the score.

Update the site's audit and journal, relevant shared contract, START_HERE/builder/planner entrypoints and WORKSTREAMS. Promote only supported general lessons into skills, not every niche's layout or asset choice. Finish with achieved local state, unresolved production gates, working preview and evidence paths. **Never declare 10/10 or domain-ready while a required check is failed/unverified.** A checklist is a bounded acceptance specification, not a guarantee of complete security, legal compliance, rankings or business success.

Use `scripts/score-audit.mjs <audit.json>` to verify evidence presence and compute separate local/launch scores. It cannot judge the truth of an evidence claim; the auditor must inspect it. Keep real launch blockers visible even when all local checks pass.
