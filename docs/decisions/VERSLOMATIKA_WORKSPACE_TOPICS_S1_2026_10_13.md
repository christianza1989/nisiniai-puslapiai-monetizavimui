## Decision and boundaries

Use an additive aggregate in the existing PostgreSQL/core, because legacy Conversation requires business/case and cannot safely represent a private pre-registration topic. Do not copy/re-author legacy discovery/creation histories or create a phantom Business/Grant/Case. Every new topic retains a stable ID and immutable owner/environment/organization/portfolio and anchor. The anchor is one of portfolio, owned discovery, owned creation, or a currently granted business. Native historical segments remain their own authoritative records; S0 composes validated relationships for related documents. Moving a topic between anchors or transferring ownership is outside S1.

S1 supports create/list/read topics, durable rename/pin/soft archive/restore and new owner-authored text records. These records are explicitly **stored without dispatch**. S1 imports no worker/model/delegation/learning/channel path and does not promise an active coordinator. No specialist/builtin agent sender can be supplied by client input or fabricated on reads. Existing runtime flags and foundation/admission remain unchanged. Later S2 must add reviewed participant/event/delegation admission using maintained task/executor infrastructure.

## Proposed exact storage

One owned migration `0031_workspace_topics.py`, down_revision `0030_site_build_candidates`, adds three private tables; no legacy rows are changed:

1. Topic: owned binding tuple, immutable anchor-kind and native nullable anchor columns, current metadata revision, message sequence, title, pin, archived timestamp, creation/update timestamps and creation source revision. A CHECK requires exactly the columns for the chosen anchor; portfolio anchor uses the existing portfolio binding, not another synthetic root. Full binding FKs target discovery/creation identities. Business anchor pins the full existing grant identity `(id,business_id,organization_id,portfolio_id,environment_id)`; replacing a revoked grant never silently revives old topic authority.
2. Message: topic ID plus full owned binding FK, immutable positive sequence, content and digest, receipt reference, server-bound author_user_id equal to the owned user, created/source metadata and literal stored_without_dispatch state. No arbitrary sender, recipient, model profile, capabilities, source revision or approval fields exist in POST input. The runtime role has SELECT/INSERT, not UPDATE/DELETE.
3. Operation receipt for **all three POST operations** (create, set_metadata, append_message): immutable request key/fingerprint/operation, full topic binding and authorizing-session FKs. One request UUID namespace per user/environment therefore rejects reuse across metadata and message operations. Metadata receipts retain an accepted metadata snapshot; message receipts reference the one authoritative immutable message rather than duplicating its text. Full binding reciprocal message/receipt FKs are deferred until commit; the operation CHECK permits a message reference only for append_message, and the FK ties the receipt back to that exact message ID. Insert receipt/message atomically with preallocated server IDs, never mutate a receipt to finish a write. Runtime has SELECT/INSERT only. Parent topic cascades allow narrowly scoped administrative fixture cleanup, with deferred NO ACTION reciprocal FKs; there is no customer delete privilege or route. This follows maintained UUID/fingerprint/locked transaction patterns, not a new generic replay service.

Replay response distinguishes accepted receipt from the current topic read. A historical metadata snapshot never carries a current can_store_message flag; a current TopicView separately reports archived/read/write state. Replayed message content comes from the exact immutable message reference. Resolve every replay behind current session/owner/anchor authority.

All tables FORCE RLS. Policies require the current local/test environment, the same verified enabled ordinary user, enabled owner membership and matching portfolio/organization; topic policies also require the actual native owned anchor or pinned enabled grant. Child policies resolve through that same current topic binding. Policies are authorization, not execution admission. Topic identity is immutable; metadata revision changes and message-sequence increments are separate clocks, with DB checks/triggers preventing unrelated field changes. Archive preserves topic/message/receipt rows; there is no customer hard-delete route. Administrative test cleanup is narrowly scoped to random test environments and never becomes a runtime privilege.

Native anchor, owner-user, portfolio and authorizing-session provenance FKs use RESTRICT, preserving the retained history when a legacy root/principal might otherwise be deleted. Only owned Topic→Message/Receipt cleanup has CASCADE; this can be exercised administratively for named random test fixtures, and runtime has no Topic DELETE. Business metadata requires the actual pinned enabled grant plus current verified owner membership; it does not require creation registration/profile/foundation admission. Nor can a shared business grant reveal another owner's legacy/S1 notes: private children retain full user/organization/portfolio/environment binding.

## Service and wire

Strict additive `workspace-topics.v1` schema and generated portal import precede UI implementation. Fixed ordinary-customer GET/POST routes reuse existing customer_guard/authenticated/current_actor, binding/digest, signed-cursor primitives and row locks. URL-bound portfolio/topic IDs and validated native anchors are checked at every request; writes recheck current session/user/membership/root under locks before commit. RLS and full native/child FKs independently refuse foreign binding. Missing migration/storage is503, never an empty result.

Create/controls/message calls require an exact UUID; metadata mutations use expected_metadata_revision and return409 on conflicts. Message sequence is allocated atomically under the topic lock. Retry resolution remains behind current authority. New text does not run quota reservation or enqueue code and cannot acknowledge provider success. Archive refuses new messages but retains read/replay access under current authority; restore is an explicit revision-bound metadata action.

Every write first resolves current authority, then reconciles the common receipt/key/fingerprint, then applies archive/CAS checks only to a new operation. The canonical request fingerprint includes operation, URL-bound target/root and validated caller material. It excludes current bearer/session ID, current source revision and current metadata/history clocks not supplied by the caller. A renewed session or release can therefore reconcile the original request while retaining original authorizing-session/source evidence. DB UNIQUE(user_id,environment_id,idempotency_key) applies once in the common receipt table to every operation; no independent message-key namespace is used.

Topic list is bounded/cursor-paged, scope/query/archive-filter bound, with typed IDs and saved metadata. Pin/title/archive changes invalidate the corresponding list snapshot explicitly; messages do not masquerade as topic metadata changes. History resumes by immutable sequence with a pinned cutoff and current authority recheck. Cursor signatures never confer permissions. Incoming structured document/reply/attachment references are deferred until their exact admission/FK/retention contract is reviewed; S1 accepts only bounded plain text.

Exact list order is pinned DESC, immutable created_at DESC, UUID DESC. Its snapshot includes identity, anchor, title, pin/archive and metadata_revision, excluding message_sequence and message-driven updated_at. Do not sort by mutable updated_at under this snapshot. History cutoff binds actor/session/environment/topic and committed message sequence; it survives rename/pin/new messages because immutable earlier history remains valid, while current access is rechecked. Bounds: title1–120Unicode code points without controls; nonblank text1–2500code points allowing only ordinary newline/tab controls; page1–50; search≤100code points; body≤16KiB; receipt accepted metadata JSON≤16KiB; integer clocks≤2147483647 with explicit exhaustion refusal. Message receipts identify the immutable accepted ID/sequence/content digest rather than only topic metadata.

## UI and acceptance

New generic topics are distinct from legacy idea/build topics and original business titles. Durable title/pin/archive controls must disclose confirmed/uncertain/conflict results and preserve account/root-scoped drafts. A confirmed store clears only the submitted unchanged draft; a retry retains the same request UUID. The UI labels these messages saved and execution not connected. A later executor must not automatically consume S1 records merely because a flag changed. Related-document inspection continues through S0 and never silently changes outgoing scope.

Required before adoption: migration schema/FK/RLS/privilege/immutability tests on existing restricted isolated PostgreSQL; foreign user/portfolio/environment/grant denial; session/membership/anchor/grant revocation; exact replay/conflicting reuse; concurrent metadata/message sequence; archived/restore and storage-unavailable paths; pagination/search/pin/change/cutoff; no worker/provider/usage/job side effects; old discovery/creation/S0 regression. Then source-safe staging, unique upgrade journal, scoped coverage and deliberate isolated adoption. Portal requires source-matched BFF tests plus actual Chrome desktop/mobile, keyboard, draft/retry/remount/late-read and new-topic CRUD paths. No main/other-PC/real-team acceptance is inferred from those checks.

The independent reviewer accepted the three-table additive shape as the smallest suitable provider-zero contract and required the incorporated cross-operation receipt namespace, caller-only fingerprints, immutable ordering/cutoff and provenance retention. Exact implementation ownership is reserved separately before code. Broad team runtime, arbitrary capabilities and commercial deployment are outside S1.
