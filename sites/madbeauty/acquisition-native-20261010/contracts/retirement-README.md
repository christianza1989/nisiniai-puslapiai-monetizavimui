# Recipient retirement v1 — candidate0.1.0

Separate strict server-only operation for a native verified account erased before or after provider creation. It does not alter [recipient-binding0.1.0](../recipient-binding-v1/README.md) or [acquisition0.1.1](../acquisition-v1/README.md). Generated [schemas](schemas.json) use [revocation.py](../../runtime/src/pinet_core/acquisition/revocation.py); regenerate/check with `uv run --locked python scripts/acquisition_retirement_contracts.py --check`.

POST `/integrations/acquisition/v1/sites/{site_id}/retire-recipient`, using the existing raw-byte acquisition transport signature and **explicit `retire-recipient` permission**. Scope/adapter/environment/target remain mandatory. Dedicated recipient and transport keys remain separate. The implemented HTTP host is isolated capture-only; the normal API is not mounted or enabled.

`RecipientRetirement` includes retirement_contract_version0.1.0, scope, adapter_id, invitation_ref, request_id, native_account_ref, occurred_at, source_release and reason account_erasure|retention_erasure. Optional recipient_proof is the **unchanged strict RecipientProofRequest** previously prepared from actual native OTP/account email; nested scope/adapter/ref/account must exactly match. No raw email, fabricated provider ID or browser identity is admitted.

Before native erasure, prepare the final proof and private retry payload inside the actual native privacy transaction/outbox, then remove pending acquisition identity/requests according to the agreed retention policy. Do not block actual erasure waiting for remote HTTP. If no core challenge/proof was ever prepared or sent, discard a private candidate locally; it has no core binding to revoke. If a proof ACK may have been lost, preserve that exact proof as the retirement evidence. A bound account can retire with its actual native account reference, without recovering a deleted email.

Core locks the scoped campaign/invitation and checks authenticated native authority. An unbound invitation requires its persisted challenge, key/rule/ref and intended-address MAC; marketing expiry/stop does not disable privacy. A wrong forwarded-link account receives candidate_retired and does not erase/stop the intended recipient. A matching bound account or matching unbound MAC receives recipient_retired: erase the private canonical recipient/account, retain a minimal scoped opaque-account fingerprint and immutable secret-free receipt, and prevent subsequent conversion. Retirement of an existing conversion makes current state account_deleted/profile_active=false; it never invents a native provider or activation event. Native lifecycle source_revision is not rewritten by the separate privacy operation.

Same operation/request UUID and **same exact bytes** returns the original secret-free receipt after expiry/stop/retirement. Changed bytes under that UUID returns409. A replayed historic recipient_bound/profile_active ACK is evidence of the earlier command, not current state or permission to reactivate. Director/report reads must use the current authoritative projection. An unseen older native lifecycle revision for the already bound provider is recorded stale after deletion, without changing the terminal state or retirement fingerprint; fresh newer activity cannot resurrect it. Wrong proof403 does not consume a nonce or bind/erase the invitation. Unknown ref404; missing unbound proof409; future retirement time422. Sender must distinguish transient transport errors from these permanent command rejections and never generate a new UUID to bypass a conflict.

Privacy retention and tombstone expiry are **not a production policy in this candidate**. The capture ledger keeps secret-free receipt/hash evidence and a scoped native-account fingerprint to prevent replay resurrection; no automatic purge or erasure-outbox job is claimed. Native privacy cleanup/outbox/retry adoption, bounded retention, key rotation and restore reconciliation must be proven before production enablement. An old backup is an old snapshot; restore to a separate isolated DB cannot certify post-erasure recovery. Reconcile authoritative later retirement/suppression facts before admitting real traffic.
